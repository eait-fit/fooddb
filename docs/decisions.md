# Decisions

Technical decisions. Business decisions are tracked outside this repo.

## Settled

| Date | Decision |
|---|---|
| 2026-10-04 | fooddb is a separate repo and service, not part of the eait backend. eait consumes the nightly snapshot. |
| 2026-10-04 | Global scope. v1 covers markets where open data is rich: US, KR, JP, TW, the Nordics, DE, FR. |
| 2026-10-04 | v1 covers both generic foods and branded products. Restaurants come later. |
| 2026-10-04 | Python for everything, the API included: uv, FastAPI, SQLAlchemy with Alembic, the official MCP SDK, Typer, Splink. |
| 2026-10-04 | Open Food Facts data stays in its own attributed layer. The API returns only core data by default, and OFF data with `include=off`. Every field carries a licence tag. The OFF-derived layer is published monthly as an ODbL dump. |
| 2026-10-04 | Customers may store what they fetch. |
| 2026-10-04 | The model layer is a port with two backends: OpenRouter, and local agents (Claude, Codex, Devin) running on the user's own licence. The hosted pipeline uses OpenRouter. When customers run the CLI or MCP server locally, they can point label reads at their own key, and the results come back as observations. |
| 2026-10-04 | Data model: values per 100 g or 100 ml, plus the serving size printed on the label. |
| 2026-10-04 | Search uses `pg_trgm` only. Known limit: short CJK names match poorly. |
| 2026-10-04 | Snapshots: the API serves the latest one by default, and `?snapshot=YYYY-MM-DD` pins an earlier one for 30 days. |
| 2026-10-04 | Brand upload form in v1. The uploader's brand is checked against the GS1 company prefix. |
| 2026-10-04 | Review UI: SQLAdmin plus one custom page that shows the photo next to the fields that differ. Agents work the same queue through the API. |
| 2026-10-04 | Hosting: on eait's infrastructure, with its own Postgres database. REST is sold through RapidAPI; MCP and CLI use our own API keys. |
| 2026-10-04 | Code licence: AGPL-3.0 (changed from Apache-2.0 the same day). Anyone hosting a modified fooddb must publish their changes. API customers are not affected. The data is licensed separately: the core data under our own terms, the OFF layer under ODbL. |
| 2026-10-04 | Products are matched entities. Every source record, barcoded or not, is matched by Splink to a product id. Barcode, name, brand, language and nutrient values are features. Matches above one probability threshold (default 0.95, configurable) merge automatically, with no human step. The resolver picks per field across all sources of a product, and the licence travels with each value. |
| 2026-10-04 | Observations carry a review status. Values that pass the checks are accepted automatically; failing values stay pending and the last accepted value keeps being served. Pending values feed the review queue. |
| 2026-10-04 | Reads: values are resolved per returned product inside each query now; a nightly snapshot table is added later, and the API switches to it for speed and `?snapshot=` pinning. |
| 2026-10-04 | Data model: each value records its basis (per 100 g or per 100 ml); kJ-only energy is converted to kcal; a field that disappears from a newer source record is withdrawn; unchanged values are not stored again. |
| 2026-10-04 | Ingest streams downloads to disk and reads them line by line. A full-dump OFF fetcher bootstraps the OFF layer before the daily deltas. |
| 2026-10-05 | Snapshot pins: `?snapshot=DAY` returns the same values for the 30 days that it is kept, once that UTC day is over. Only today's snapshot is written, and a rebuild on the same day (the nightly build, or a fetcher's first data) replaces it. Thus a pin on today can change until the day ends. A merge after a build does not change a snapshot's values: a read collects the values of every product merged into the one asked for. Records and names stay live. |
| 2026-10-05 | Access: writes, the review queue and `/admin` always need an API key. Reads need one only when `FOODDB__BACKEND__REQUIRE_KEY_FOR_READS=true`. The default keeps a self-hosted read API public. Our hosted API sets it. Keys are stored as PBKDF2-HMAC-SHA256 under the server secret, so a leaked table cannot be checked against guesses without it, and a new secret retires every key. The rate limit is a per-minute window in Postgres, shared by all replicas. stdio MCP is local and needs no key. |
| 2026-10-05 | Licence tags: each served field is an object `{value, source, licence, record}`, not a flat value with a separate provenance map. Thus the tag stays with the value when a consumer copies one field, and the shape matches `per_100`. Each barcode is tagged with the most trusted record that has it. A field with no value is `null`. API version 0.3.0. |
| 2026-10-05 | Resolver rule for nutrient values, in this order: a value older than the newest candidate by more than `FOODDB__BACKEND__STALE_AFTER_DAYS` (default 730) loses. Then the value that the most distinct sources agree with wins (within 5 %, or 0.5 in the unit). Then trust rank, then the newest value. Agreement comes before rank, not only as a tie-breaker: a label read is a machine read and can be wrong, and two independent sources that agree are stronger evidence. Records of one source count as one vote, so OFF duplicates cannot outvote a table. |
| 2026-10-06 | Nutrient codes: store both carbohydrate codes and tag each value by its source. Nothing is converted between codes. `CHOCDF` (by difference, with fibre) comes from FDC nutrient 1005 and from OFF labels sold only in the US or Canada. `CHOAVL` (available, without fibre) comes from OFF labels sold only in the EU, UK, Switzerland, Norway, Iceland, Liechtenstein, Australia or New Zealand. OFF's `carbohydrates-total` is `CHOCDF`. Any other OFF label is `CHOCDF` with the flag `carbs-regime-unknown`. `ENERC_KCAL` stays the canonical energy, and `ENERC_KJ` is also kept when the source states kJ. Atwater with `CHOAVL` adds fibre at 2 kcal/g (EU 1169/2011, Annex XIV). No data migration: the stored OFF data has no market, so an old `CHOCDF` value cannot be re-coded. A delta with a newer edit of a product re-codes it and withdraws the old code. |
| 2026-10-06 | Wrong merges: every merge is logged in `merge_log`, and a reviewer can split one. A split writes a cannot-link pair between each record that moves and each record that stays. Matching never puts both records of such a pair in one product. It adds pairs to products strongest first and skips a pair that would break a constraint. Thus a cluster splits at its weakest pairs. A split product gets its old id back when the log shows that id merged away. Otherwise it gets a new id. Constraints are per record, not per product, so they survive later merges. Matching itself still never splits a product. |
| 2026-10-06 | ODbL dump: on the 1st of each month (04:00 UTC), the worker dumps the newest final snapshot day. The dump holds what the API serves under ODbL with `include=off` that day, and nothing else. A line is a product with at least one OFF record. It keeps the product id, only the `off:` record ids, and only the fields, barcodes and values tagged `ODbL-1.0`. A field that a core record gives is `null`. Thus no CC0 or core value is in the dump, and the product id links each line back to the API. An OFF value that lost to a core value is not served, so it is not in the dump. `/v1/dumps` needs no API key, also when reads need one, because ODbL publication must be open. It counts against the rate limit. The newest 3 dumps are kept. [data-licence.md](data-licence.md) states the attribution and the share-alike obligation. |
| 2026-10-06 | Label reads: a read from the server's model is served without review only when its confidence is at or above `FOODDB__BACKEND__LABEL_CONFIDENCE_FLOOR` (default 0.9) and the checks pass. Below the floor, every value is pending. A read that the client did on its own subscription and sent with the photo is never served without review, whatever confidence it claims. The demo backend reports confidence 0. Evidence: each photo is stored once by its SHA-256 in `FOODDB__BACKEND__PHOTO_DIR`, and only JPEG, PNG and WebP by magic bytes, at most 10 MiB, pass. One photo is one source record, `label:<sha256>`, with the licence `LicenseRef-fooddb`. Each observation names its photo in `observation.evidence`. Uploads need the new `contribute` scope, which `review` and `admin` imply. The OpenRouter default model is `qwen/qwen3-vl-235b-a22b-instruct`, because the account reaches only x-ai and Chinese-vendor models. |
| 2026-10-06 | Ranges per category are conservative. A value out of range waits for review, so a range flags only a value that no real product of the category has. A range implicates only the field out of range. A record with no fooddb category gets no range check. The category comes from the source's own tags (OFF `categories_tags`, FDC food category) through one table in `checks.py`. |
| 2026-10-06 | Warning seals (Chile, Mexico, Peru) are computed from the served values on each read, not stored and not reviewed. They are tagged with source `fooddb` and the most restrictive licence among the values they read. fooddb has total sugars, fats and sodium, not added ones, so a computed seal is an upper bound on the label. Only one direction is a check: a seal that OFF says the pack carries, but that the values do not reach, holds the values that the seal reads. |
| 2026-10-06 | CIQUAL cell values: a number is the value. `traces` is 0, because the amount is too small to measure and 0 is what a label shows for it. `< x` (under the limit of quantification x) gives no value, not x/2 or x: a bound is not a measurement, and an invented value would pass the checks and win in the resolver. `-` (not analysed) gives no value. A field with no value falls back to the other sources of the product. The same rule applies to other tables that use trace and limit marks. |
| 2026-10-06 | Trust rank for nutrient values, highest first: `brand`, `label`, the composition tables (`fdc`, `ciqual`, `fineli`, `matvaretabellen`, one rank), `off`. Tables are curated and have a method and a date, so they outrank crowd edits. They share a rank because none of them is more trusted than the others for its own foods. Between tables, agreement and then the newest value decide. |
| 2026-10-06 | New sources: CIQUAL (`etalab-2.0`), Fineli (`CC-BY-4.0`) and Matvaretabellen (`NLOD-2.0`) go into the core layer. Their licences ask for attribution. Thus each product lists the attribution of the sources of its served fields, and [data-licence.md](data-licence.md) states the texts. FDC Branded Foods (CC0) is off by default (`FOODDB__BACKEND__FETCH_FDC_BRANDED`), because it is about 3 GB of JSON. Fineli is off by default (`FOODDB__BACKEND__FETCH_FINELI`), because fineli.fi refuses automated downloads. A source that is off is not fetched, not scheduled and not in `/healthz`. |
| 2026-10-06 | An unverified brand upload is fully pending. The GS1 check is a port, and its only backend is `none` (answers `unknown`), because GS1 access has a cost that is not decided. Until a verifier answers `verified`, every value of an upload waits for review, with the flag `brand-unverified`. A record with no accepted value does not name a product, tag its barcode or answer a lookup. Thus nothing that a brand uploads, and no low-confidence label read, is served before review. |
| 2026-10-06 | Approved label reads: a label read that a reviewer approved in the review queue always wins. It has source `label`, status `accepted` and a `reviewed_by`. It wins over every other candidate of its product and nutrient, before staleness and agreement. This supersedes "agreement before rank" of the 2026-10-05 row for such reads. Of several approved reads, the newest wins. A label read that the checks accepted alone has no `reviewed_by` and keeps the old rule. A rejected or pending read never wins. Brand uploads get no override, because the GS1 verifier governs them. `snapshot_value.approved` stores the flag, so the merge-follow of a snapshot read applies the rule exactly. |
| 2026-10-07 | The pack price is VAT-inclusive: the EUR 29.99 that we advertise is the final price, because EU consumer prices include VAT. The inline Checkout price therefore sends `tax_behavior=inclusive` and the tax code `txcd_10000000`, and does not rely on the Stripe account defaults. Both are configurable (`STRIPE_TAX_BEHAVIOR`, `STRIPE_TAX_CODE`). A Price set by `STRIPE_PRICE_ID` carries its own tax behaviour. With `STRIPE_AUTOMATIC_TAX` on, Checkout also collects the billing address. Until a live VAT registration exists, no VAT is collected. ([#46](https://github.com/eait-fit/fooddb/issues/46)) |
| 2026-10-06 | Selling access ([#44](https://github.com/eait-fit/fooddb/issues/44)): a pack of 100,000 requests costs EUR 29.99, paid once through Stripe Checkout, and the credits do not expire. There is no free tier. Reads need a key (`FOODDB__BACKEND__REQUIRE_KEY_FOR_READS=true`) and the portal sells it. A user signs in by magic link, with no password: a mailed token, stored hashed, single use, valid 15 minutes. An account owns its keys and they share one credit balance, so a customer can make a key per app. Each read with such a key costs one credit, and zero credits answers 402. Keys that have no account (ours) and RapidAPI-proxied requests are never charged, and an unlimited account is counted but not refused. Writes are not charged. fooddb calls the Stripe REST API with httpx and checks the webhook signature itself, so it adds no dependency. |
| 2026-10-07 | MEXT ([#38](https://github.com/eait-fit/fooddb/issues/38), `mext-free-use`). MEXT's Q&A (1-11) says that books and apps need no permission to use the table, and asks users to cite it as "日本食品標準成分表（八訂）増補2023年から引用". Thus commercial reuse is allowed and the obligation is attribution. MEXT names no standard licence, so the tag is ours. The attribution names the edition, so the fetcher stops when the page is no longer that edition. The table states carbohydrate three ways: `CHOAVL` (available, by mass), `CHOAVLM` (available, in monosaccharide equivalents) and `CHOCDF` (by difference). fooddb stores `CHOAVL` and `CHOCDF` as stated, and not `CHOAVLM`. Cells follow the CIQUAL rule: `Tr` and `(Tr)` are 0, and `-` is no value. A number in brackets is an estimate that MEXT prints as the value of the food, and its own energy values use it, so it is the value. About two thirds of the available-carbohydrate values are in brackets, so leaving them out would remove most of them. A dagger after a number is a note mark. The main table has no sugars and no saturated fat. They are in separate tables: see the entry for #57. |
| 2026-10-07 | Frida ([#35](https://github.com/eait-fit/fooddb/issues/35), `CC-BY-4.0`) is on by default. frida.fooddata.dk sends its Excel file by e-mail and has no public address for it. But DTU Data (a figshare repository) holds the same file under CC BY 4.0, and its record API lists the newest version. The fetcher uses that record, so it needs no form and no setting. Frida states both carbohydrate quantities, so fooddb stores both as stated: parameter 170 (by difference, fibre included) is `CHOCDF`, and parameter 172 (available, without fibre) is `CHOAVL`. Frida writes a trace as 0, so a number is always the value. A blank cell is no value. |
| 2026-10-07 | CoFID ([#36](https://github.com/eait-fit/fooddb/issues/36), `OGL-UK-3.0`) states carbohydrate and sugars as monosaccharide equivalents. Their weight is about 5 % lower, and the user guide gives only approximate factors: 1.05, and 1.10 for starch. fooddb stores neither as `CHOAVL` or `CHOCDF`. The value would overstate the weight, and a conversion would invent a number. The other sources of a product give its carbohydrate instead. CoFID stores energy, protein, fat, AOAC fibre, saturates and sodium. `Tr` is 0 and `N` is no value, as for CIQUAL traces. Alcoholic beverages are per 100 ml. CoFID gives the code 13-669 to two foods, so neither is stored. The file of old foods is not read, because the publisher has not reviewed those foods since 2008. |
| 2026-10-07 | TFDA ([#39](https://github.com/eait-fit/fooddb/issues/39), `OGDL-Taiwan-1.0`) is under the Open Government Data License, version 1.0. It allows any use, commercial use included, and requires a notice that names the provider, the data and the licence (data.gov.tw/license, section 3.2). The licence asks for a year and a version. The table is a rolling update with no versions, so the attribution names the dataset and its data.gov.tw number. TFDA's `總碳水化合物` equals 100 minus water, ash, protein, fat and alcohol, so it is carbohydrate by difference. fooddb stores it as `CHOCDF`, and the table has no `CHOAVL`. Its `糖質總量` is the sum of its six sugars, so it is `SUGAR`. Energy is `熱量`, which follows the factors of 4, 9 and 4 kcal/g that the energy check uses. `修正熱量` is TFDA's own modified figure, and fooddb does not store it. The rows of sample means are skipped, because they only average samples that the table already lists. The table has no trace marks. A blank amount is no value. |
| 2026-10-04 | Health means freshness: each fetcher's last successful run within its schedule, shown in `/healthz` and `./dev status`. |
| 2026-10-07 | Request log ([#48](https://github.com/eait-fit/fooddb/issues/48)): one `request_log` row per API request, written by one ASGI middleware. A row stores the time, method, route template, status, latency, response bytes, key id and name, account id, and an 8-hex-digit HMAC of the client address. It never stores the raw URL, the query, a header or a token, so barcodes and search terms stay out. An unmatched path is stored as `(unmatched)`. The address hash uses `FOODDB__BACKEND__SECRET_KEY` and keeps only 32 bits, so it tells clients apart for abuse checks but is not the address, and without the secret nothing is stored. `/livez`, `/healthz` and `/admin` are not logged. Rows are deleted after `FOODDB__BACKEND__REQUEST_LOG_DAYS` days (default 30) by a daily job. Admin actions (run now, grant credits, set unlimited, revoke key) write `admin_action` rows with the admin key name. They are POST forms with a CSRF token in the admin session, because SQLAdmin's own actions are GET links. |
| 2026-10-07 | Alcohol ([#53](https://github.com/eait-fit/fooddb/issues/53)): fooddb stores ethanol as `ALC`, in g per 100 g or per 100 ml like the rest of the row. The Atwater check adds `7 × ALC` when the record has it (EU 1169/2011, Annex XIV). The check lives in `checks.py` only, and it names `ALC` among its implicated fields. A wine or a spirit then passes, and a figure that the alcohol does not explain still fails. FDC (nutrient 1018), CIQUAL, CoFID (`ALCO`), Fineli, Frida (parameter 19), Matvaretabellen (`Alko`), MEXT and TFDA (`酒精含量`) map to `ALC`. OFF has no gram value: its `alcohol` is a percentage by volume. fooddb does not convert it. |
| 2026-10-07 | MEXT sugars and saturated fat ([#57](https://github.com/eait-fit/fooddb/issues/57)). The main table has neither, so the fetcher also reads two files from the same page, joined on the food number: `FASAT` from the fatty acid book (`脂肪酸成分表編`, 第2章第1表, g per 100 g of edible part), and `SUGAR` from the carbohydrate book (`炭水化物成分表編`, 第2章本表). `SUGAR` is the sum of glucose, fructose, galactose, sucrose, maltose, lactose and trehalose. Each is in its own mass. The monosaccharide-equivalent column `CHOAVLM` is not used. Trehalose is a disaccharide, so it counts, as in Frida's mono- and disaccharide sum. Starch and the sugar alcohols do not count. A `-` (not measured) adds nothing, and `Tr` is 0, the rule of the main table. For 961 of the 1,026 foods that state starch and available carbohydrate, available carbohydrate minus starch minus this sum is within 0.25 g. The other 65 (starch syrups, bean paste, Japanese sweets) hold dextrins and oligosaccharides that the book does not list, so their `SUGAR` is the measured sugars only. A food that a table does not list gets no value from it: 1,967 of 2,538 foods have `FASAT` and 1,094 have `SUGAR`. Neither adds a failed check to any food of the 8th edition 2023 supplement. The run stops when the identifier or the unit of a column changes, when the page has no link to a table, or when one food number has different names in two tables. The ref is now the three file names, so the next run reads the tables even though the main file did not change. |
| 2026-10-07 | The admin **Label reads** page became **Review** at `/admin/review`: one card per food record of any source with pending values, with each failed check explained by the numbers it compared, every latest value next to the value served now, and accept and reject that return to the page. A `next` redirect target must be a path under the admin mount. `review.queue` keeps its output unless a caller asks for `detail`. |
| 2026-10-07 | API contract: fooddb keeps its own contract and does not imitate Open Food Facts. `GET /v1/products/{barcode}` returns `{items: [...]}`, 422 for a code that is not a valid GTIN and 404 for no product. Search is `GET /v1/foods?q=`, a product is `GET /v1/foods/{product_id}`, and a source record is `GET /v1/records/{record_id}`. `?snapshot=` pins a day and `?include=off` adds the OFF layer. There is no compatibility endpoint for OFF clients (`/api/v2/product/{code}.json`): do not build one. |
| 2026-10-07 | Admin panel: stay on SQLAdmin 0.32 and rebuild the experience. Compared on 2026-10-07: starlette-admin 1.0.2 (MIT, 2026-10-03, Tabler like SQLAdmin, so the same look; its 1.0.0 of 2026-08-16 rewrote list rendering), SQLAdmin 0.32.0 (BSD-3-Clause, 2026-09-20, 2.8k stars), fastapi-amis-admin 0.7.3 (Apache-2.0, 2025-03, SQLModel, no release in 12 months), Piccolo Admin 1.14.0 (MIT, Piccolo ORM only), FastAPI-Admin 1.0.4 (Apache-2.0, 2022, Tortoise ORM and Redis), FastAdmin 0.10.0 (MIT, its own model registry), and a React SPA (react-admin or Refine, MIT) on our JSON API. No candidate gives a better look than the Tabler UI that we already have, and every one needs the login, the Review page, the split and decide actions and the audit rows ported. The SPA needs a Node build in the image and a CRUD API that fooddb does not have. "Not great" was the layout, not the library: a flat menu, empty page headers, a landing page with nothing on it, bar tables for charts, raw floats, lists with no filters. Now: menu sections, a dashboard with inline-SVG charts and a needs-attention list, filters and row actions on the lists, sortable and filterable tables, a key-only login. No new dependency, no build step. |
| 2026-10-08 | OFF product photos in the admin: hotlink, store only a reference ([product-images.md](product-images.md), recommendations 1 and 2). The Review card of an `off:` record shows the 400 px front and nutrition photos from `images.openfoodfacts.org`, lazy, with `referrerpolicy="no-referrer"` and the credit "Photo: Open Food Facts contributors, CC BY-SA 3.0" linked to the product page and the licence. The reference (`lang` and `rev` per kind) is read at ingest into `food.images`, a nullable jsonb column on the record, because it is metadata of one source record that follows the same upsert and the same older-file guard as the other metadata, so a changed photo updates the row and adds no observation. `{}` means OFF has no photo, null means not asked. fooddb stores and serves no image bytes, and the public API, the snapshots and the ODbL dump do not carry the reference. A backfill job for the records stored before the column (`fooddb run off-images`, only OFF records with pending values, about 870 on prod) reads OFF's API at 7.5 products a minute, half of the documented 15 a minute per IP, and nothing schedules it. OFF's folder rule pads every barcode to 13 digits, so an EAN-8 has no folder of its own. Customer-facing images stay deferred until the legal review (CC BY-SA on images that fooddb returns) and the choice of an object store are decided. |

## Open

1. **GS1 prefix check.** GS1's public GEPIR lookup has mostly been replaced by "Verified by GS1",
   which may require a paid GS1 membership. Find out what access costs. The brand upload form
   waits for the answer: its verifier is `none` until then.
2. **Legal review.** How far ODbL reaches into served answers, and whether training a model on
   OFF's CC BY-SA photos is allowed. Also whether an API that returns OFF image URLs, or a
   mirror of the images, is a Collection or an Adaptation under CC BY-SA 3.0. No customer sees an
   image before the answer ([product-images.md](product-images.md#decisions-for-kirill)).
